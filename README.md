# Passing Isn't Proof

**Silent Bugs and Local-First Escalation in Small Code Models**

Code, result tables, journal paper and seminar report for a Technical Seminar research project at
Pimpri Chinchwad College of Engineering (PCCOE), Pune.

- **Author:** Aahil Sayed (Third Year B.Tech, Computer Engineering, PCCOE, Pune; group GA12)
- **Guide:** Prof. Dr. Swati V. Shinde (Dean MIS, PCCOE, Pune)

## What this is

Small code models running locally can match much larger cloud models *when hidden unit tests pick the
best of k samples* (Hassid et al., COLM 2024). A developer never has those hidden tests. This project asks
what is left of that result when the selection is done with checks a developer really has:

| strategy | how the answer is chosen |
|---|---|
| S0 | first sample |
| S1 | oracle best-of-k (hidden tests; the upper bound, not a realistic check) |
| S2 | first sample that passes the public example cases |
| S3 | sample that passes the most model-written tests (threshold tau, primary tau = 1.0) |
| S4 | majority vote over program outputs |
| S5 | example cases and majority vote combined |

**Research questions**

1. **Gap.** How much of the accuracy gap between a local small model and a cloud LLM do realistic checks recover?
2. **Silent bugs.** How often is code accepted by a check still wrong on the hidden tests (false-pass rate), and what kind of failure is it?
3. **Escalation.** If the local model's answer is sent to the cloud only when the check rejects it, how much work stays local and what accuracy is lost?
4. **Thinking.** Is one long "thinking" sample from a small model worth more than several short ones?

**Models.** Local (Ollama, consumer-class GPU budget of about 7 GB VRAM): Qwen2.5-Coder 1.5B and 7B,
DeepSeek-Coder 6.7B, Qwen3-4B with thinking off (k = 5) and on (k = 1). Cloud: GPT-OSS-120B (Groq) and
DeepSeek-V3.1, non-thinking (SambaNova).

**Benchmarks.** LiveCodeBench `code_generation_lite`, 182 problems with contest dates 2025-01-04 to 2025-04-06
(primary), and a fixed random 200 of MBPP+ (strict EvalPlus hidden tests).

In words (LiveCodeBench, GPT-OSS-120B as the cloud model):

- The best local configuration reaches 31.9 % against 54.4 % in the cloud. Realistic checks recover only
  about 13–21 % of the gap; even the oracle S1 recovers only 15–23 %. Most of the gap is in medium and hard
  problems that no local sample solves.
- Checking against the examples alone (S2) accepts code that is wrong on the hidden tests 31–39 % of the
  time (20–25 % on MBPP+); majority vote alone is worse on LiveCodeBench (40–54 % for the three
  stronger models, 82 % for the 1.5B). Requiring both (S5) is the only check with
  consistently lower false-pass rates (14–30 % LiveCodeBench, 13–16 % MBPP+).
- Local-first escalation with S5: Qwen2.5-Coder-7B keeps about 20 % of problems local and reaches 52.7 %
  against 54.4 % all-cloud; on MBPP+ it keeps 85 % local at 79.0 % against 80.0 %.
- Qwen3-4B thinking is the best single local sample (31.9 %) but costs 6.6 k tokens per sample, and 64 % of
  samples hit the 8,192-token cap.
- DeepSeek-V3.1 (non-thinking) reaches only 32.4 % on LiveCodeBench (79.0 % on MBPP+): 121 of its 182 answers hit
  the frozen 1,024-token output cap while still explaining, and 111 of them contain no complete program; 59 of the 71
  answers with a complete program pass (83 %). Against it the local models close far more of the gap (Qwen2.5-Coder-7B
  S5: 45 %), and local-first escalation even beats it (7B with S5: 33.5 % vs 32.4 %). The 2025-03-01 split
  (34.3 % before vs 30.0 % after) shows no clear contamination signal; every model drops a few points after that date.

The paper (PDF on the GitHub Release `v1.0`) has the full tables, confidence intervals and McNemar tests.

## Repository layout

| path | contents |
|---|---|
| `slmcheck/` | the harness: download, prepare, generate, execute, select (S0–S5), evaluate, verify gates, report |
| `tests/` | pytest suite on fixtures (no models needed) |
| `results/livecodebench/`, `results/mbppplus/` | result tables (CSV), `RESULTS.md`, verification report and notes for each benchmark |
| `tools/` | independent manual checker, contamination split, README table |

Raw runs (`runs/`), the full bundle with raw samples (`bundle/`, `slmcheck_bundle.zip`, about 110 MB) and
downloaded data (`data/raw/`) are not in git. The bundle and the paper PDF are attached to
the GitHub Release `v1.0`.

## Reproducing

Windows PowerShell shown (the original runs); on Linux/macOS use `.venv/bin/python`. Every step is resumable:
if something stops, fix the cause and rerun the same command.

### 1. Setup

```powershell
git clone https://github.com/aahil62/slm-seminar seminar
cd seminar
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pytest -q          # fixtures only, no models
```

Local models (Ollama; the explicit `qwen3:4b-q4_K_M` tag matters, the stock `qwen3:4b` tag is now thinking-only):

```powershell
ollama pull qwen2.5-coder:1.5b
ollama pull qwen2.5-coder:7b
ollama pull deepseek-coder:6.7b
ollama pull qwen3:4b-q4_K_M
```

Cloud keys are read from the environment only: `GROQ_API_KEY` (GPT-OSS-120B) and `SAMBANOVA_API_KEY`
(DeepSeek-V3.1). Set them with a hidden prompt (for example `Read-Host -AsSecureString` in PowerShell) so they never appear in a
file, log or chat, then open a new shell. `SLMCHECK_OLLAMA_URL` points the
harness at a non-default Ollama server; `SLMCHECK_PARALLEL` sets in-flight requests for local configs.

Dry run without any model: `python -m slmcheck all --fake --run-dir runs/dryrun --out runs/dryrun_bundle`
(output labelled `FAKE — NOT RESULTS`).

### 2. Data

```powershell
python -m slmcheck download
python -m slmcheck prepare --run-dir runs\main
python -m slmcheck download --benchmark mbppplus
python -m slmcheck prepare --benchmark mbppplus --run-dir runs\mbpp
```

### 3. Gates (all must PASS; a FLAG must be explained)

```powershell
python -m slmcheck verify --stage env     --run-dir runs\main
python -m slmcheck verify --stage data    --run-dir runs\main
python -m slmcheck verify --stage exec    --run-dir runs\main
python -m slmcheck verify --stage backend --run-dir runs\main
python -m slmcheck verify --stage data    --run-dir runs\mbpp
```

### 4. Smoke run (3 problems, every config)

```powershell
python -m slmcheck prepare --run-dir runs\smoke
python -m slmcheck all --run-dir runs\smoke --limit 3 --out runs\smoke_bundle
```

### 5. Generate

```powershell
python -m slmcheck generate --tier slm --run-dir runs\main
python -m slmcheck generate --tier slm --run-dir runs\mbpp
python -m slmcheck generate --tier llm --run-dir runs\main
python -m slmcheck generate --tier llm --run-dir runs\mbpp
```

`--tier llm` runs both cloud configs (`gpt-oss-120b` on Groq, `deepseek-v3.1` on SambaNova); HTTP 429 rate
limits are waited out automatically.

### 6. Evaluate, verify, report

```powershell
python -m slmcheck evaluate --run-dir runs\main
python -m slmcheck verify --stage post --run-dir runs\main
python -m slmcheck report --run-dir runs\main --out bundle\livecodebench
python -m slmcheck evaluate --run-dir runs\mbpp
python -m slmcheck verify --stage post --run-dir runs\mbpp
python -m slmcheck report --run-dir runs\mbpp --out bundle\mbppplus
```

Independent spot checks (plain `subprocess`, not the harness executor):
`python -I tools/manual_check.py runs\main 8 5 5 41`.

## Known limitations

- **Contamination.** Qwen3 (April 2025) overlaps the LiveCodeBench window; DeepSeek-V3.1 (August 2025) was
  released after it, so its LiveCodeBench numbers are also reported on the 2025-03-01+ split. MBPP+ (2021) is
  likely contaminated for every model: use it for checker strictness, not absolute accuracy.
- **Small window.** Only `test5`/`test6` of LiveCodeBench exist, so 182 problems; the post-2025-03-01 split is about five weeks.
- **One cloud sample.** Cloud models ran with k = 1 (greedy, temperature 0); local multi-sample configs drew
  sample 0 greedily and samples 1–4 at temperature 0.8, top-p 0.95.
- **qwen3-4b-think k = 1** (agreed fallback), so S1–S5 cannot be measured for it, and 64 % of its LiveCodeBench
  samples hit the frozen 8,192-token cap (9 % on MBPP+).
- **Shared GPU.** Runs used an RTX PRO 4000 Blackwell shared with another job (about 7 GB VRAM free) with
  concurrent requests; wall times are not laptop timings and batched decoding causes small run-to-run differences.
  Use `completion_tokens` as the cost measure.
- **Output cap.** The frozen 1,024-token cap for non-thinking configs truncates most of DeepSeek-V3.1's
  LiveCodeBench answers, so its 32.4 % is a lower bound for this model under a looser budget.
- **Llama-3.3-70B** was planned as the second cloud model but was unavailable on every free or low-cost
  provider tried (October 2026), so DeepSeek-V3.1 replaced it.
